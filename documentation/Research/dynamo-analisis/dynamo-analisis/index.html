🔁 SACA DEL WORKFLOW

El bucle, a un programa (dynamo)

El script de un dynamic workflow no puede ejecutar comandos ni leer ficheros. Por eso cada git/gh pasa por un agente Haiku (runner) que lo copia a mano. Pásalo a un orquestador propio (recomiendo TypeScript, ver Python o Node) que llame a git/gh directamente y use claude -p solo para el Builder y el Reviewer.

⛔ NO HAGAS

«Solo skills» para el modo desatendido

Si un LLM orquesta el bucle, el bucle deja de ser determinista y vuelves a lo que tu plan descarta (regla 6, §3; research §3.2): permisos que se quedan esperando en la sesión, sin coste en USD por ticket y con el contexto del coordinador llenándose. El propio Pocock usa código para el modo AFK: Sandcastle (TypeScript, run({ maxIterations })).

Sobre lo de que «los workflows son para tareas enormes»: es verdad a medias. Un dynamic workflow rinde cuando hay muchos agentes que piensan repartidos en abanico (migraciones: un agente por fichero más un revisor adversarial). Tu bucle tiene 2 pasos que piensan por ticket y unos 9 que son entrada/salida. El problema no es el tamaño. El bucle con X intentos, en código

Un boceto del núcleo, en TypeScript. Lo que en run.js necesita runner, páginas y fingerprints aquí es una llamada a execFile. boceto sin probar --agent, --agents, --json-schema, --max-budget-usd y --permission-prompts son flags documentados de claude; compruébalos con claude --help en tu versión.

const MAX_ROUNDS = 2
const mergeLock = new Mutex()                        // merge en serie, carpeta principal

async function runTicket(t: Ticket, base: string): Promise<Outcome> {
  const wt = await worktreeAdd(t, base)             // git worktree add (execFile)
  await moveCard(t, 'Build')
  let failure: string | undefined
  for (let round = 1; round <= MAX_ROUNDS; round++) {
    const b = await agent('builder', buildPrompt(t, base, round, failure),
                          { cwd: wt, schema: BuildOut, budgetUsd: 3 })
    if (b.data.needsHuman) return block(t, 'build', b.data.needsHumanReason)
    await moveCard(t, 'Verify')
    const sha = await git(wt, 'merge-base', 'HEAD', base)
    const bad = (await runChecks(wt, sha)).filter(r => r.code !== 0)
    if (bad.length) { failure = render(bad); await moveCard(t, 'Build'); continue }
    await moveCard(t, 'Review')
    const r = await agent('reviewer', reviewPrompt(t, base),
                          { cwd: wt, schema: ReviewOut, tools: READ_ONLY })
    if (r.data.verdict === 'PASS')
      return mergeLock.run(() => merge(t, wt, base, { costUsd: b.costUsd + r.costUsd }))
    failure = r.data.report; await moveCard(t, 'Build')
  }
  return block(t, 'rounds', failure)
}
async function agent<T>(role: string, prompt: string, o: AgentOpts<T>) {
  const def = resolveRole(role)                      // .dynamo/agents/ > plugin/agents/
  const args = ['-p', prompt, '--agents', JSON.stringify({ [role]: def }), '--agent', role,
    '--output-format', 'json', '--json-schema', JSON.stringify(toJsonSchema(o.schema)),
    '--max-budget-usd', String(o.budgetUsd ?? 2),
    '--permission-mode', 'auto', '--permission-prompts', 'none']
  if (o.tools) args.push('--allowedTools', o.tools.join(','))
  const { stdout } = await execFileAsync('claude', args, { cwd: o.cwd, env: AGENT_ENV })
  const out = JSON.parse(stdout)
  if (isUsageLimit(out)) throw new UsageLimit(out)   // el bucle duerme y reanuda
  return { data: o.schema.parse(structured(out)),    // zod valida el contrato
           costUsd: out.total_cost_usd, turns: out.num_turns }
}

export async function main(tickets: number[], base: string, parallel = 2) {
  for (;;) {
    const state = await readBoard(tickets, base)     // GitHub = estado
    const ready = frontier(state)                    // función pura, testeada
    if (!ready.length) break
    await pMap(ready, t => runTicket(t, base), { concurrency: parallel })
  }
  console.log(await releaseReport(base))             // push y PR: los haces tú
}

1 · ¿Python o Node?

TypeScript sobre Node (y Bun para el binario)

Los dos valen y la arquitectura es idéntica en ambos. Lo que inclina la balanza son tres cosas. Ya tienes código y tests en JS. Los dynamic workflows y Sandcastle son TypeScript. Y con bun build --compile sacas un ejecutable único para Windows, macOS y Linux, que es lo más cómodo para instalarlo en proyectos sin Node, como una app KMM. juicio propio

CriterioTypeScriptPython

Qué decide

  • Continuidad: outside-writes.js, fake-gh.js, harness.js y la lib de #76 ya son Node. Con Python lo reescribes todo.
  • Distribución: npx dynamo, o un binario con bun build --compile --target=bun-windows-x64. En Python el equivalente es uv tool install, que también funciona bien.
  • Contratos tipados: zod valida la config y genera el JSON Schema para --json-schema. En Python, pydantic hace lo mismo.
  • Opción B viva: si algún día quieres fan-out dentro de una sesión con /workflows, se escribe en el mismo lenguaje.
  • Para ti: vienes de Kotlin, y TS te da tipos estáticos y async/await, muy parecido a las corrutinas.

Si prefieres Python, nada del diseño cambia: asyncio + pydantic + uv. super-board es Python + bash y funciona.

El onboarding en cinco pasos

1Investigar

Lo que se ejecuta de verdad: los workflows de CI primero, luego los scripts (package.json, tareas de Gradle, Makefile), luego README y CONTRIBUTING. También el git log, para ver dónde y con qué nombre se añaden los tests. Cada dato se apunta con su fuente.

2Entrevistar

Solo lo que no se puede deducir, como hace /discover: qué no se toca, cuál es el ejemplo canónico, qué tests son lentos o inestables y qué necesita macOS o secretos.

3Redactar

Un borrador de AGENTS.md. Si ya existe, propone un diff en vez de reescribirlo. El bloque dynamo va entre marcadores.

4Demostrar

Cuatro pruebas por comando: que se reproduce, que detecta un fallo (el canario), que la selección por cambios no oculta fallos y que cabe en el tiempo. Los resultados se anotan en el propio fichero.

5Aprobar

Tú revisas el diff de AGENTS.md: una sola puerta, como la de /to-tasks. La fontanería (tablero desde plantilla, ramas y pre-push, etiquetas, plugin) va en una línea.

La prueba del canario: ¿tus tests detectan algo?

En una copia desechable, Dynamo mete un fallo pequeño en una línea con cobertura (le da la vuelta a una comparación o cambia un valor devuelto) y lanza verify.fast. Si sigue en verde, esa red no atrapa nada. Es la idea del mutation testing, reducida a tres o cinco canarios.

Qué se hace con una zona ciega: va a AGENTS.md como «Zonas sin red». Un ticket que la toque pide el test primero (la regla 2 del Builder pasa de aconsejarse a exigirse con un when), o pasa por un gate. Y abre un ticket de deuda en el backlog. propuesta

La plantilla

Un AGENTS.md que sirve a la vez a personas, agentes y motor

Unas 150 líneas como mucho, como tus skills. Lo largo se enlaza a docs/ o a las fuentes de conocimiento. Lo que más ayuda a un agente es un ejemplo canónico por cada tipo de cambio: «para un endpoint nuevo, copia src/api/users.ts». Funciona mejor que diez reglas abstractas. propuesta

# AGENTS.md · mi-web

## Qué es
Tienda web: Next.js + API en src/api. Pagos vía Stripe.

## Mapa
- src/app/       páginas (App Router)
- src/api/       handlers; un fichero por recurso
- src/domain/    lógica pura, sin I/O
- e2e/           Playwright

## Cómo se hacen las cosas aquí
- Endpoint nuevo: copia src/api/users.ts (validación zod + test)
- Lógica en src/domain/, nunca en componentes
- Fechas: date-fns, nunca new Date() en dominio

## Cómo se escribe un test aquí
- Vitest, junto al fichero: total.ts → total.test.ts
- Canónico: src/domain/cart/total.test.ts (AAA, sin mocks)
- UI: Testing Library por rol, nunca por clase CSS
- e2e: e2e/<feature>.spec.ts con tag @ticket-<n>

## No tocar
- src/payments/ sin gate humano
- migraciones ya publicadas

## Zonas sin red          (lo escribe el canario)
- src/utils/format.ts: sin tests; test primero

## Conocimiento
- docs/architecture.md · Obsidian «Proyecto Web/Dominio»

Se mantiene vivo

dynamo doctor repite las pruebas si cambia la CI, un lockfile o un fichero de build (los compara por hash). Si una ejecución falla por algo que AGENTS.md pudo evitar, el paso de conocimiento propone el diff como ticket y tú lo apruebas. Es la idea de /reflect de pstack.

Lo que no va aquí

Ni ids del tablero ni ramas: eso va en .dynamo/config.yaml. Tampoco procedimientos largos: esos van como skills del proyecto en .claude/skills/, que se cargan solo cuando hacen falta.

Y en cada ticket

No basta con que pase: el test nuevo tiene que fallar sin el cambio

SWE-bench valida así cada parche: los tests FAIL_TO_PASS fallan sin la solución y pasan con ella, y los PASS_TO_PASS pasan en ambos casos. Un estudio de ACM sobre SWE-bench encontró parches «plausibles» pero incorrectos que pasaban con tests débiles. El motor puede hacer esto sin LLM, con tests.new y tests.single de AGENTS.md.

en la base (sin el cambio)en la rama del ticketveredicto

Un paso prove nuevo

Va entre verify y review. Si no hay test nuevo, o si pasa también en la base, el ticket vuelve a Build: «el test no prueba el cambio». Si la base es una zona sin red, no se acepta un ticket sin test.

Tests que no se debilitan

Un check determinista sobre el diff: ningún fichero de test borrado y ningún patrón de tests.forbidden añadido. Hoy eso es la regla 6 del reviewer y depende de lo que diga un LLM.

reviewer.md:51 «a deleted, skipped or weakened test is a failure»

Cada criterio, con su prueba

La plantilla de ticket añade «Prueba» a cada checkbox: el nombre del test o el comando. /to-tasks lo pide, el Builder escribe ese test y prove comprueba que existe y que pasa de rojo a verde.

Mutation testing, solo si hay riesgo

Stryker (JS/TS), PIT (JVM/Kotlin) o mutmut (Python), solo sobre las líneas cambiadas y con when en módulos críticos. Es caro, así que entra cuando los datos lo pidan.

Con AGENTS.md como fuente de cómo se trabaja, la config se queda en lo que no es de ningún agente: repo, tablero, límites y fuentes de conocimiento. Es la evolución de tu factory.json, con un campo version y un esquema. propuesta

  - kind: obsidian

    role: builder
    column: Build

  - id: verify

    column: Verify
    onFail: build
  - id: prove
    run: fail-to-pass           # rojo en base, verde aquí
    column: Verify

    column: QA

  - id: review

      - role: reviewer-security

    aggregate: { role: approver, minConfidence: 80 }
    onFail: build
  - id: gate
    when: "changed('src/payments/**')"   # «No tocar»
  - id: merge
    run: merge                  # --no-ff, verify, revert
    column: Done
    onFail: needs-human

5 · Review con varios agentes a la vez

Panel por riesgo, verificación por confianza y un agregador

Así funciona el plugin oficial code-review de Anthropic: agentes en paralelo con enfoques distintos (cumplimiento de CLAUDE.md, bugs, historial de git) y luego una puntuación de 0 a 100 para cada hallazgo, quedándose solo con los de ≥80. En Code Review de Claude Code el orden es encontrar, verificar, ordenar y publicar.

El de alcance, siempre

«¿Se sale del ticket?» es el fallo más común de un agente desatendido. Spotify veta 1 de cada 4 sesiones por eso. Es barato y es lo que mejor funciona de tu reviewer actual.

Los especialistas, según el riesgo

Seguridad si cambian auth/ o SQL, UI si cambian componentes, tests si cambia lógica. Con when en el pipeline, cada revisor extra solo se paga cuando hay riesgo.

«most ordinary programming tasks do not need a panel of 5 reviewers» (research §3.6)

Verificar antes de devolver

Cada hallazgo pasa por una puntuación de confianza antes de mandar el ticket de vuelta a Build. Un falso FAIL te cuesta una ronda entera.

6 · Modularizar los agentes de cada paso

Un rol es un contrato, no un prompt

Cada paso pide un concepto (rol) con entrada, salida y permisos fijos. Cumplirlo puede un agente de Claude, otro proveedor o incluso un comando determinista. El motor resuelve el rol con este orden: .dynamo/agents/ del proyecto, luego el plugin y luego el valor por defecto. Después lo pasa con --agents/--agent.

+ · Conocimiento del proyecto

Repo, Obsidian o Confluence: los agentes siempre leen ficheros

No sabes dónde vivirán tus docs, así que no ates los agentes a ninguna fuente. El motor resuelve las fuentes en un context pack por ticket, dentro de la copia: ficheros Markdown con su origen y su fecha. Los agentes leen ese pack. Cada fuente es un adaptador.

FuenteCómo leerlaDesatendidoCuándo
Repo (docs/, ADRs, AGENTS.md)Lectura directa por globs✅ determinista y versionado con el códigoya
ObsidianUn vault es una carpeta de Markdown: se lee del disco, con include y resolviendo [[wikilinks]]. Hay MCP opcionales (plugins de Obsidian o servidores remotos)✅ si el vault está en la máquinacuando un proyecto lo use
ConfluenceAtlassian Rovo MCP (https://mcp.atlassian.com/v2/mcp, OAuth 2.1 o API token para headless), o un sync por API a una caché Markdown⚠️ mejor sync antes del run: un OAuth a mitad de -p se queda colgadocuando un proyecto lo use

Qué va en cada sitio

Reglas cortas en CLAUDE.md/AGENTS.md (se cargan siempre). Cómo se hace algo en skills propias de .claude/skills/ (se cargan bajo demanda y llegan a las copias). Contexto largo, como dominio, arquitectura o API, va en las fuentes de conocimiento.

Seleccionar, no volcar

El pack lleva lo marcado como always, las referencias que cita el ticket (añade «References» a la plantilla) y lo que pidan las etiquetas del rol. Volcar todo llena el contexto (research §7.8).

Hoja de ruta multi-proyecto

Cada capacidad entra cuando un proyecto la pide

El orden es el mismo de la parte 1, ampliado. El disparador de cada fase es un hecho medible, no una idea.

F0

Cierra 0.1.0 y saca el motor (en Dynamo)

Motor TS con el bucle mínimo (build → verify → review → merge), el bloque dynamo de AGENTS.md (el de Dynamo es el primero), config.yaml v1 con un esquema e interfaces Board, Runner y Knowledge con una sola implementación cada una. Dynamo se construye con él.

Disparador: ninguno, es la parte 1.

F1

Segundo cliente: tu web

Plugin + /dynamo-setup: AGENTS.md de la web demostrado con canarios, paso prove y tablero desde plantilla. El conocimiento sale del repo. Es la etapa 4 de tu plan.

Disparador: la primera lista de la web termina en un PR sin intervención.

F2

Pipeline declarativo + QA

Tipos role, run, gate y when, y un rol qa con capturas de Playwright contra los criterios de aceptación.

Disparador: un ticket pasa los checks y la review pero falla en el navegador.

F3

Panel de review por riesgo

parallel + aggregate, puntuación de confianza y memoria de hallazgos.

Disparador: encuentras en el PR de release fallos que el reviewer dejó pasar (con cifras).

F4

Perfil KMP + CI con macOS

Checks JVM y Android en el bucle; iOS en la CI de la release o en un Mac.

Disparador: empiezas la app KMM.

F5

Adaptadores y backends extra

Obsidian y Confluence, el Agent SDK y Codex.

Disparador: un proyecto tiene sus docs ahí, o hay datos de que otro modelo revisa mejor.

Lo que no construiría: una interfaz propia (regla 5: el tablero ya es la UI), varios proveedores desde el primer día, todos los adaptadores de conocimiento por adelantado, ni el auto-merge a main. Ninguna empresa de tu research lo hace (§6.3).
